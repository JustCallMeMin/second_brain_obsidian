---
description: Propose consolidation, corrections, restructuring, metadata completion, companion repair or source recovery as a diff
argument-hint: <finding or request>
---

Maintenance request: $ARGUMENTS. Follow CLAUDE.md and GLOSSARY.md. This is a single operation: any failed write or verification stops it with a report.

You may propose consolidation, correction, restructuring, conflict resolution, adding or completing frontmatter, companion repair and source recovery. You may **not** write anything until the user approves.

1. Identify the exact files affected. Run `python3 scripts/kb.py lint --json` as the baseline. Apply the CLAUDE.md dirty-tree rule to every target: snapshot status and sha256; a dirty or untracked target is touched only if the approval names that file; offer a checkpoint commit, never make one unprompted.
2. Show the change as a diff per file. A rename or deletion is its own explicit line; never do either silently.
3. Metadata completion for a file with no frontmatter (W10) or incomplete frontmatter (E02): propose `type` (from folder and content), `created` = file creation date and `updated` = max(created, file modification date), both labeled as estimates. For a text source: `original` (double-quoted; the processed name of the original when it is in `inbox/processed/`, or re-derived from the source's `created` and the capture's name for a pending capture), but **never derive `sha256` from a candidate original** (that makes recovery verification circular): a lost `sha256` stays missing, and recovery then stops. For malformed frontmatter (E01): propose the minimal syntax fix.
4. Conflict resolution: show the edit that removes the callout(s) and the knowledge text that replaces them; both claims stay visible until the user decides. Removing a pair of callouts uses the CLAUDE.md both-or-neither sequence; if either note is blocked, remove neither, never call the conflict resolved, and list both paths and the reason under **Needs attention** with the words "still requires attention". Never touch a source body.
5. **Source recovery** (a damaged text source, such as a truncated body). Candidate originals: the file named by the source's `original` in `inbox/processed/`, and a capture still in `inbox/` whose `shasum -a 256` equals the source's stored `sha256` (interrupted ingest; lint W05 finds it). Verify: the candidate's sha256 must equal the stored `sha256`; ignore any candidate that does not. If both copies verify, use the one in `inbox/processed/` and say so. Check the candidate for secrets with `kb.py lint --json` (W07): on a finding, stop, report file and line, print nothing. If the source's own frontmatter is invalid, complete it first with its own diff (step 3). Rebuild like ingest step 4: `printf` the source's existing frontmatter fields, then `cat` the candidate, into a hidden temporary file in `sources/` (snapshot it as absent); `cmp` the rebuilt body against the candidate (unwrapped if the original had its own frontmatter) **before anything is replaced**. Keep a copy of the damaged source in the scratchpad. Snapshot the source's hash and show the full replacement (frontmatter included) and its hash as a diff. If there is no verified candidate (original missing, hash mismatch, stored `sha256` unreadable): stop, report, write nothing, never overwrite; the fallback is restoring the source from git history. Never ask the user to delete the source first when a verified candidate exists. Never convert encodings. Never write before the user explicitly approves a diff that names the source file. After recovering from a pending capture tell the user to re-run `/ingest` (it resumes).
6. **Companion repair** (E08, or a companion missing `sha256`): locate the binary through the companion's `original` if that file exists, else through the `![[...]]` embed in its body, else by sha256 if still readable, else ask the user to name it; propose the corrected `original` (double-quoted) and, if needed, `sha256` computed from that binary as a diff, and write only after approval naming the companion. Never "recover" a companion's body from the binary.
7. Wait for explicit approval; the diff header lists every dirty or untracked target so the approval can name them. Apply exactly the approved diff; for existing knowledge notes use exact-string edits; replace a recovered source with `mv` of the verified temporary file (same folder) and `cmp` the result against the candidate again. Verify each target's sha256 equals the snapshot immediately before writing (for a recovery also re-hash the candidate; it must still equal the stored `sha256`); on any mismatch write nothing, report, and stop (retrying needs a new approval). If the `mv` succeeded but the final `cmp` fails, stop, report, and offer to restore the kept copy only with a new approval.
8. Set `updated` only if knowledge text or links changed, not for whitespace, formatting or metadata-only edits (`tags`, `aliases`, `confidence`, `standalone`), and not when completing frontmatter (step 3 sets it). Never change a source body except through approved source recovery.
9. When the request comes from an ingest that stopped on an unresolved ERROR, W10 or E07 (E01/E02 in a note it created or edited, an invalid companion, a missing citation), repair only what the diff shows and delete or roll back nothing. For E07 name file and line only, show no diff and ask the user to edit the note by hand (never redact). After the repair tell the user to re-run `/ingest`: it resumes and finalizes only if lint shows no error in the capture's files.
10. Run `kb.py lint --json` again, compare with the baseline by `id` (counting repeats), and report any new ERROR, every file changed, and a **Needs attention** section for anything skipped.
