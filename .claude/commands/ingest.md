---
description: Ingest captures from inbox/ into sources and, only when warranted, knowledge notes
argument-hint: [capture filename ...]  (default: every pending capture)
---

Ingest captures. Follow CLAUDE.md and GLOSSARY.md (classification, basename rule, names, dirty-tree rule, failure isolation, conflicts). Arguments: $ARGUMENTS

**Classify each capture** per CLAUDE.md. Text (`.md`/`.txt`, valid UTF-8): source copy plus original in `inbox/processed/`. Binary (everything else): moved as-is into `sources/`, no copy, no separate original file. Non-UTF-8 `.md`, extension-less and empty captures: blocked. Symlink: skip and report. A non-UTF-8 `.txt` is binary and never scanned.

**Failures.** Isolated (block that capture or only the dependent part, record the reason, continue): suspected secret, non-UTF-8 `.md`, empty/extension-less/symlink/unreadable capture, a created name that still violates the basename rule, a post-move failure whose rollback verified, a retry that finds an unresolved ERROR, W10 or E07 in the capture's own files (direct the user to `/maintain`; delete or roll back nothing), duplicate, corrupt source, a retry whose planned filename is taken, a not-yet-written target that was dirty or changed since its snapshot, capture changed after hashing, a skipped conflict, validation failure confined to this capture's own known writes. If any knowledge part is skipped, or an ERROR, W10 or E07 remains in a file this capture created, the capture is **not finalized**: skip step 7, leave it in `inbox/` as partially ingested, and a later run resumes it. Run-level (stop the whole run; process nothing more; report completed, failed and pending captures, every file written and **every Needs attention entry so far**; clean up nothing): `kb.py lint` cannot run or exits 2; a file this run already wrote (a conflict partner included) changed since its last recorded hash; a failed or partial write, move or verification (snapshot, disk, permission, `git status` errors included); a rollback or undo that fails or cannot be verified; a new ERROR or new W10 outside the files written for this capture. Never print a suspected secret.

**Once per run.** List the files you expect to write and apply the dirty-tree rule; re-apply it to any target that appears later.

**Execution discipline.** Process one capture at a time. Never put several captures, or a write together with the check that verifies it, into one loop or script that keeps going after a failure. Check every verification by its exit status, never by silence: for example `cmp a b && echo CMP_OK || echo CMP_FAIL`, and treat anything but the OK marker as a failure. This applies to `cmp`, hash comparisons, `mv -n`, `git status` and every write to the scratchpad (snapshot file, saved baseline). A run-level condition stops the run where it happens: do not finalize the current capture and do not start the next one.

For each capture, in order:

1. **Baseline.** Immediately before its first write run `python3 scripts/kb.py lint --json` and keep it. If a W07 finding names this capture, do not open, ingest, modify or redact it; report file and line and ask for review.
2. **Already ingested?** Compute and record `shasum -a 256` of the capture.
   - Text, a source has that `sha256`: body does not match the capture (`cmp`) = corrupt. Body matches and its `original` is in `inbox/processed/` = completed earlier: report the duplicate and ask before moving it. Body matches but that original is not there (interrupted, partially ingested, or a fresh clone) = resume with the **resume procedure** below; the processed name is the source's stored `original`; never create a second source.
   - Corrupt also means a source whose `original` is this capture's name under any date prefix and whose `sha256` is missing or unreadable. Stop this capture, do not repair it here, and tell the user `/maintain` can rebuild the source from this capture or from the original in `inbox/processed/` once its hash verifies against the stored `sha256`, with a diff and approval (no deleting first). If the stored `sha256` is unreadable there is nothing to verify against; the fallback is restoring the source from git history.
   - Binary: the same sha256 in `sources/` (the binary, or a companion whose binary is there) = duplicate: report and ask before moving it. A companion with that sha256 whose binary is not yet in `sources/` = interrupted: reuse the companion; the binary's final name is the companion's `original`; if that name is now taken by a different file this capture fails (isolated) and you point to `/maintain`. Otherwise look for knowledge notes that already link its planned `sources/` filename (`kb.py backlinks <filename>`) and apply the resume procedure to them.
**Resume procedure** (R1 to R6; any capture that has a source but is not finalized; no manifest; "step N" below means ingest steps):
   - **R1.** Re-read the source (binary: the binary and its companion).
   - **R2.** Run `kb.py lint --json` (binary: with `--pending <planned filename>`, tolerating only that one target's E04/E08 left by a verified rollback). The capture's files are the source, the companion, every knowledge note that cites the source (`kb.py backlinks <source>`, which also scans a note with malformed frontmatter as raw text; `sources:` lists) and every note whose Conflict callout cites one of those. Any ERROR, W10 or E07 in them is an **unresolved failure of a previous attempt, never baseline**: stop this capture (isolated), list each finding, direct the user to `/maintain`, delete or roll back nothing. A pre-existing knowledge note the capture edited stops it too (its error cannot be told apart from the capture's own). For E07 name file and line only; the user edits by hand; nothing is redacted. Only when those files are clean take this attempt's baseline (step 1).
   - **R3.** Reconstruct the expected contributions from the source with the step 5 rules: target path, kind (new note, additive update, progress entry, conflict callout, hub, decision) and expected content.
   - **R4.** Check each target independently, both ways. *Present*: the target cites the source at that place and contains the content. *Missing*: the target path does not exist, or the target has no citation of the source for it. Otherwise *unclear*. Every knowledge note that cites the source must map to a reconstructed contribution; one that does not (renamed, or reconstructed differently) makes the related contribution *unclear*, never missing.
   - **R5.** Apply only the missing contributions under the dirty-tree rule; do not touch present ones (no duplication). If any is unclear, or the list cannot be reconstructed reliably, show the evidence, ask the user, and write nothing for it; never guess.
   - **R6.** Finalize (step 7) only when every contribution is present and step 6 passes.

3. **Plan and snapshot.** List every file to create, edit or move and apply the dirty-tree rule to each. A dirty or untracked target needs explicit approval naming it, otherwise skip that part and report. Check name collisions case-insensitively; a collision suffix goes before the extension. Never overwrite or rename.
4. **Provenance.** Names you create must satisfy the basename rule (processed name: ingestion date as prefix, which is also the source's `created`; a collision with any file in `inbox/processed/` or `sources/` gets the suffix before the extension).
   - Text: for a new source fix the processed name now and record it as `original`, double-quoted; a resume reuses the stored value. Build `sources/<kebab-name>.md` with the shell (`printf` the frontmatter: `type: source`, `created`, `updated` = created, `sha256`, `original`, optional `url` double-quoted; then `cat` the original) and verify the body with `cmp`. If the original has its own frontmatter, keep it verbatim in a fenced yaml block at the top of the body. Every text capture gets a source, including the user's own raw thoughts.
   - Binary: no copy. Plan its kebab-case filename in `sources/` and cite that name; it moves in step 7. Create a companion only if useful: `sources/<kebab-name>.md` with `type: source`, `created`, `updated` = created, `sha256` = the binary's sha256, `original` = the binary's exact final filename in `sources/` (for example `"playwright-guide.pdf"`), body embedding `![[playwright-guide.pdf]]`. Create no other file for the binary's original.
5. **Knowledge.** Create or update knowledge notes only for reusable knowledge or learning progress; otherwise stop at the source. A binary contributes only through notes you write after reading it, citing its planned filename.
   - Search first (`kb.py search`, `kb.py backlinks`). Updates are additive: never rewrite or delete existing text without a diff and approval.
   - Decision: own file only with real alternatives and reusable rationale, else a bullet under `## Decisions` in the project overview. Lesson: reusable → knowledge note in `notes/`; project-specific → `## Lessons` in the overview.
   - Progress: append `- YYYY-MM-DD: text` under `## Progress` of the topic note, using the capture's explicit event or completion date, else today. Create a topic note only for a meaningful subject that warrants ongoing tracking; for a trivial, isolated activity create none and end at the source.
   - A project overview that lists a technology needs a knowledge note for it: create a short topic hub if none exists and report it.
   - Conflict between two knowledge notes: use the CLAUDE.md both-or-neither sequence. Each `> [!warning] Conflict` cites the other note with a wikilink and the source of the claim it adds, and states both claims. If either note is dirty and unapproved or changed since its snapshot, or the second edit fails and the first is undone and verified: write neither, never say it is resolved, add a **Needs attention** entry (both note paths, the reason, "still requires attention") to the final report, and create no marker in the vault unless the user explicitly approves one. The capture is then not finalized (it stays in `inbox/` and a later run resumes it). If the first note changed before the undo, stop the run.
   - Conflict where one claim exists only in a source: a single callout in the knowledge note citing the source (same Needs attention entry if that note is blocked). Never modify the source; record its file content hash before and verify it unchanged after.
   - **Every contribution cites its source** with a wikilink in the added text, bullet, progress entry or callout (`sources:` in a new note); this is what makes resume checkable.
   - Set `updated` to today only when knowledge text or links changed, not for whitespace, formatting or `tags`/`aliases`/`confidence`/`standalone`. New knowledge notes cite their source in `sources:`. Never add frontmatter to an existing file that lacks it.
6. **Validate.** Run `python3 scripts/kb.py lint --json` (binary: add `--pending <planned filename>`, once; it tolerates that one target in notes' links and in a companion's `original`). Compare finding `id`s with the baseline, counting repeats. Pass = (a) no ERROR whose `id` is not in the baseline and no new W10, and (b) **no ERROR, W10 or E07 at all in any file this capture created in any attempt** (source, companion, new notes), baseline or not. Baseline errors elsewhere do not block (report them). A failure of (b), or of (a) confined to this capture's own writes, leaves the capture pending (not finalized, isolated); the next attempt's resume procedure stops on it and points to `/maintain`. Other warnings, REVIEW and PENDING never block; a new E07 blocks and is reported without redacting anything. Fix your own mistakes in files written in this attempt and re-run. A failure confined to this capture's own writes is isolated; a new ERROR anywhere else is run-level. While the capture is still in `inbox/`, W05 (same content as its new source) and W08 (its basename equals the source's) on the capture itself are expected; they clear after step 7.
7. **Finalize.** Verify the capture's hash still equals the recorded one (if not, stop this capture). Text: create `inbox/processed/` if absent (`mkdir -p`) and move it to the processed name. Binary: move it to `sources/<kebab-name>` and re-run lint **without** `--pending`: no new ERROR and no E04 or E08 for the planned filename. On failure move the binary back to `inbox/` under its original name; never delete knowledge notes or the companion and never revert edits; if the move back fails or cannot be verified, stop the run and report both paths. On any earlier failure the capture stays in `inbox/`.
8. **Report** once after the last capture (or at a run-level stop): files created, edited, moved; completed, blocked and skipped captures with reasons; **Needs attention** (skipped conflicts; captures stopped on an unresolved error, each finding with the `/maintain` direction; new E07; baseline errors left alone). Then offer a checkpoint commit (never make one unprompted).
